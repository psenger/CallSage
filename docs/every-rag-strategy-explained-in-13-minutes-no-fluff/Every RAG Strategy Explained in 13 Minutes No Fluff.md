# [Every RAG Strategy Explained in 13 Minutes No Fluff](https://www.youtube.com/watch?v=tLMViADvSNE)
> Cole Medin

Here's a more detailed breakdown of all 11 strategies from the video:

---

**The Big Picture**

RAG has two phases: **data preparation** (chunking documents, embedding them, storing in a vector database or knowledge graph) and **retrieval/generation** (taking a user query, embedding it, searching for similar chunks, and feeding those to an LLM to produce an answer). The video argues that most production-quality RAG systems should combine 3–5 of these strategies together, not just pick one.

---

**1. Re-Ranking**

This is the presenter's go-to, used in almost every implementation. The problem it solves is simple: if you dump 20–50 raw chunks into an LLM, you overwhelm it and get poor answers. So instead, you do a two-stage retrieval. First, cast a wide net and pull a large number of candidate chunks from your vector database. Then pass those through a specialized **cross-encoder re-ranker model** that scores each chunk's actual relevance to the query. Only the top-scoring chunks get sent to the LLM. The cost is modest — you're running a second (smaller) model — but the quality improvement is significant because the LLM receives fewer, higher-quality chunks.

**2. Agentic RAG**

Rather than hardcoding a single search path, you give the AI agent multiple retrieval tools and let it decide which to use based on the question. For example, one tool might do a standard semantic similarity search across chunks, while another might retrieve and read an entire document end-to-end. The presenter demonstrated this with a Postgres/pgvector setup on Neon, where one table stores chunks and another stores full document metadata. The agent picks the right approach per query. The upside is flexibility; the downside is **unpredictability** — you need very clear tool descriptions and instructions so the agent makes good choices consistently.

**3. Knowledge Graphs**

This layers a **graph database** on top of your vector store. Instead of only finding chunks that are semantically similar to a query, you can also traverse structured relationships between entities (people, organizations, concepts, events). You typically build the graph by having an LLM extract entities and relationships from your raw documents, producing a web of nodes and edges. The presenter recommends a library called **Graffiti** for this. The major trade-off is that graph construction is **slow and expensive** because every document needs an LLM extraction pass. But for data where relationships matter — like organizational structures, legal cases with many parties, or research literature — it's extremely powerful.

**4. Contextual Retrieval (Anthropic's approach)**

Anthropic published research showing significant retrieval accuracy gains from this technique. The idea: before you store a chunk, you use an LLM to generate a short preamble that explains how that chunk fits within its parent document. This preamble gets prepended to the chunk text, and the whole thing gets embedded together. So when you later search, the embedding carries not just the chunk's own meaning but its broader documentary context. The presenter showed this in his Neon database — each chunk starts with a contextual description, followed by a triple-dash separator, then the actual content. The cost is an **LLM call per chunk during indexing**, which makes data preparation significantly slower and more expensive.

**5. Query Expansion**

One of the simplest strategies. Before the user's query hits the vector database, you pass it through an LLM with instructions to make it more specific and detailed. You define prompt instructions that tell the LLM how to add relevant details that will improve retrieval precision. For example, a vague query like "meeting action items" might get expanded to include specific project names or date ranges. The trade-off is straightforward: **one extra LLM call per search**, adding latency.

**6. Multi-Query RAG**

Similar in spirit to query expansion, but instead of refining one query, you use an LLM to generate **multiple different phrasings** of the same question. All variants get sent to the vector database in parallel, and the results are combined. This gives you broader coverage — different phrasings might surface different relevant chunks that a single query would miss. The cost is the initial LLM call plus **multiple database queries** instead of one, but the parallel execution helps mitigate latency.

**7. Context-Aware Chunking**

This shifts focus to the **data preparation** side. Naive chunking (splitting every 1,000 characters) breaks documents at arbitrary points, which ruins embedding quality and loses document structure. Context-aware chunking instead uses an embedding model to detect **natural boundaries** in the text — paragraph breaks, topic shifts, section changes — and splits there. The result is chunks that represent coherent units of meaning. The presenter specifically recommends **Dockling**, a Python library that implements **hybrid chunking** (a form of context-aware chunking). It's more complex to set up than naive splitting but the presenter considers it very worth it.

**8. Late Chunking**

The most complex and the only one the presenter hasn't personally implemented. The conventional approach is: chunk first, then embed each chunk independently. Late chunking flips this. You run the **entire document through the embedding model first**, producing token-level embeddings that carry full-document context. Then you chunk the token embeddings. The result is that each chunk's embedding inherently understands the surrounding document, solving the "lost context" problem without needing an LLM to add contextual preambles (like strategy #4). It leverages longer-context embedding models. The downside is substantial implementation complexity.

**9. Hierarchical RAG**

This creates **parent-child relationships** between chunks at different granularity levels. You search at the small/precise level (individual paragraphs or sections) to find the most relevant hit, but then you can "zoom out" and pull the parent chunk or even the full document for broader context. These relationships are stored as metadata. The presenter demonstrated this in Neon: find a relevant chunk, look at its metadata to identify the source document, then optionally retrieve that full document from the document metadata table. It's essentially a way to **search small but return big**. The presenter notes this is arguably a subset of agentic RAG, and it adds similar complexity and unpredictability.

**10. Self-Reflective RAG**

A self-correcting feedback loop. After the initial retrieval, you call an LLM to **grade the relevance** of the returned chunks (e.g., on a 1–5 scale). If the grade falls below a threshold (say, 3), the system automatically retries with a refined query. This catches cases where the initial search missed the mark. The cost is at least one additional LLM call after every search for the grading step, and potentially more if retries are triggered. But it adds a safety net that improves reliability.

**11. Fine-Tuned Embeddings**

Rather than using a general-purpose embedding model, you **fine-tune** one on your domain-specific data. The presenter's research found **5–10% accuracy gains**, and noted that a small fine-tuned open-source model can outperform larger commercial ones on your specific use case. The key insight is that you can change *what* similarity means. A pre-trained model treats "my order was late" as similar to "shipping was fast" (both about order logistics). But with a sentiment-focused training set, you can make "my order was late" most similar to "items are always sold out" (both negative customer experiences). The trade-off is significant: you need a **substantial training dataset**, infrastructure to train and host the model, and ongoing maintenance.

---

**The Presenter's Recommended Starting Combo**

If you're picking just three: **Re-ranking + Agentic RAG + Context-Aware Chunking** (hybrid chunking with Dockling). Stack: Postgres with pgvector, hosted on Neon. The GitHub repo linked in the video has pseudocode for all 11 strategies plus a combined reference implementation.
